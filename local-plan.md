# Local-first SQLite with required cloud sync

## Context
The mobile app currently reads and writes financial data through Convex; Expo SQLite, an outbox, and a sync-engine skeleton exist but are not mounted or used by screens. Implement the user's requested hybrid local-first behavior: persist data in SQLite and show local edits immediately, synchronize every local edit automatically to required Convex cloud storage, download a configurable recent window (default 30 days), fetch cloud data whenever a requested date range is not fully cached, and retain fetched history locally without automatic eviction. Allow a previously authenticated user to view and edit their cached data offline; process durable queued edits when connectivity returns. Surface real sync state and retry from a top-right Home icon.

## Approach

1. **Add a timestamped, idempotent cloud sync contract before changing mobile callers.**
   - Extend `convex/schema.ts` with a per-user monotonic sync cursor/change log and durable operation receipts keyed by `(actorId, clientMutationId)`. Changes must include entity/table, cloud document ID, monotonically increasing revision, server `updatedAt`, tombstone or current public document snapshot, and scope for any authorized shared-group member that needs the change.
   - Add authenticated paginated bootstrap/change/range endpoints under `convex/sync/`: bootstrap returns the authenticated user's profile/defaults, settings, owned accounts/categories/budgets/goals/recurring rules, group memberships and permitted group data, plus transactions dated within the configured recent window and required aggregate snapshots; change pagination advances the durable cursor and carries tombstones; range fetch returns all documents and related rows for a requested inclusive-start/exclusive-end date range. Reject invalid date ranges and cap page sizes. Scope every response to the current identity and group membership.
   - Add an indexed owner/time-range query for transactions and equivalent query coverage for dated group expenses, settlements, contributions, notifications, and other existing date-indexed records; the existing `transactions.by_owner_occurredAt` index is the starting point. Include related accounts/categories/groups/members/payers/participants needed to render returned rows. Record cache coverage only after every page succeeds.
   - Make every existing Convex mutation callable from active mobile screens replay-safe by accepting a `clientMutationId`, recording the result and change revision atomically with the write, and returning the original result on replay instead of applying the action twice. Include create/rename/archive/icon/limit/default/profile/group/expense/budget/transaction actions already exposed in `convex/accounts/mutations.ts`, `convex/categories/mutations.ts`, `convex/budgets/mutations.ts`, `convex/groups/mutations.ts`, `convex/transactions/mutations.ts`, and `convex/users/mutations.ts`. Keep their existing authentication, ownership, validation, and multi-record transaction behavior. Preserve create dependencies and return the canonical Convex ID so the client can map local IDs.
   - For an update queued with local modification timestamp `clientUpdatedAt`, compare it to the current record's cloud `updatedAt`: newer timestamp wins; preserve the losing record/edit in a reviewable conflict record and report conflict status rather than silently deleting either version. Define deterministic tie handling (cloud version wins an equal timestamp). Keep audit/history and both candidate payloads until explicitly resolved. This is timestamp last-write-wins with conflict visibility; device clock skew can affect which copy is newer.
   - Run `bunx vitest run tests/convex` and `bun run typecheck` after backend contract/schema changes.

2. **Replace the SQLite shell with a versioned, user-scoped financial replica and atomic repository.**
   - Evolve `app/mobile/local/sqlite/database.ts` using SQLite migrations (`PRAGMA user_version`); preserve the existing database and outbox data where migratable. Add indexed, relational cache tables for the app's authenticated profile/settings, accounts/account memberships, categories, transactions/tags, groups/memberships/invites, expense payers/participants, settlements, budgets, goals/contributions, recurring rules, notifications, receipts metadata, sync coverage/cursor, local-to-cloud ID mappings, per-record versions, tombstones, and conflict copies. Keep Convex auth-account/session secrets out of the replica.
   - Scope every user-visible record, cursor, setting, ID mapping, and outbox operation by the authenticated app-user ID. Store stable local IDs as TEXT and Convex IDs as TEXT; encode `int64` values as decimal TEXT and decode exactly to `bigint` (do not round through JS `number`). Add SQLite indexes for owner/date, account/date, category/date, group/date, and foreign-key access paths used by current screens and ranges.
   - Persist `Local Sync` days in the existing `localMetadata` table, per user/device, default `30`; choices are `7`, `30`, `90`, `180`, `365`, and `All history`. Window changes enqueue a backfill; they never delete records already cached. Only the initial bootstrap window is governed by this choice; every older range fetched on demand remains on-device indefinitely. Master/reference entities required by any cached range always bootstrap.
   - Make a local repository API provide atomic `read`, `upsertCloudPage`, `applyLocalMutationAndEnqueue`, `markSynced`, `markFailed`, `markConflict`, coverage, mapping, and status subscriptions. A write and its outbox entry must commit in one SQLite transaction. Read subscribers must update immediately after the transaction and after cloud pages/change batches are applied.
   - Store modification timestamp, base cloud timestamp/version, client mutation ID, device ID, dependency local IDs, status, attempts, next retry time, and sanitized last error for each queued operation. Fix the existing outbox schema/storage omission of `clientMutationId`; recover rows left `syncing` after process termination as retryable.
   - Protect finance cache at rest: enable Expo SQLite SQLCipher through the `expo-sqlite` config plugin and supply a per-installation random key stored in `expo-secure-store`; support existing DB migration by opening/migrating the same file once under the new key. If the installed Expo SDK/config-plugin cannot enable SQLCipher, stop before shipping plaintext financial cache and report the exact build prerequisite rather than silently falling back.

3. **Build the sync coordinator on the repository and cloud contract.**
   - Add one coordinator mounted from `app/mobile/app/_layout.tsx`, activated only after the existing Convex Auth provider has validated an identity. Persist a validated app-user ID in SecureStore after successful online authentication; allow local reads/writes for that same user when Convex is disconnected, and lock the local namespace on sign-out/account switch without deleting that user's retained cache. Never allow offline identity selection to expose a different user's cache.
   - At first authenticated startup, run bootstrap for the default 30-day window and persist each page. On app foreground and Convex reconnect, resume bootstrap/backfill/change pulls and drain the durable outbox immediately; after app/process restart, recover and resume pending operations. Online writes trigger immediate flush; retry transient failures automatically with bounded backoff (1s, 2s, 4s, 8s, 15s, then 30s cap). Serialize same-record/dependent operations and continue independent queue entries. Manual retry resets failed retry scheduling and triggers a flush.
   - Preserve dependency order: when a local-created account/category/group has no cloud ID, hold queued operations that reference it; after create sync returns, atomically map IDs and rewrite dependent payload references before dispatch. Never mark a write synced before the corresponding server receipt/change revision is stored locally.
   - Pull cloud changes using the per-user cursor and apply each page, tombstones, ID mappings, and cursor in one SQLite transaction. Use timestamp conflict behavior from step 1 for edits from other devices; keep both versions inspectable. Server validation/permission errors remain visible as failed entries with last error and retry/edit action; transient connection errors stay retryable.
   - Use Convex connection state and React Native `AppState` for immediate reconnect/foreground sync. Local writes must succeed while offline once SQLite commits. Durable pending work is resumed when the app reopens; do not claim delivery while the OS has suspended or killed the process.

4. **Move reads to the SQLite-first hybrid repository and preserve current query semantics.**
   - Replace screen-level direct `useQuery(api.*)` data reads with typed repository hooks. Return a fully covered SQLite date range immediately; if coverage is absent or partial, issue the authenticated Convex range request, display any already-cached rows without waiting, persist the complete response, then render the now-cached requested range. Deduplicate concurrent requests for the same user/range. Never mark incomplete/failed paging as covered.
   - Bootstrap/update non-date reference data and account/group/profile/settings lists so forms work instantly offline. For date-bounded ledgers, dashboard/analytics/activity/category/budget/group/person/account history, define exact range requests and cache coverage. Historical aggregates must remain correct: use cloud aggregate snapshots for all-time account balances and other unbounded totals, apply unsynced local ledger deltas immediately, and fetch/cache underlying dated rows when a screen requests a historical range.
   - Keep existing server filters and financial calculations: only posted and non-deleted/non-voided transactions count; transfer debits/credits both accounts correctly; date bounds remain start-inclusive/end-exclusive; ownership/membership and currency filters remain identical. Reuse pure domain functions where they exactly match these semantics.
   - Migrate every active data-backed read identified by `useQuery(api.*)` from reconnaissance: Home/dashboard, groups and group/person pages, profile, accounts list/detail, categories list/detail/overview, budgets list/detail, analytics, transaction composer, budget/category composers, group expense composer, and settings/profile lookups. Include list/detail dependencies and names needed by cached screens. Preserve current loading/empty/error rendering while showing cached results before network completion.
   - Change `BackendConnectionNotice` so a Convex disconnect does not cover or block already cached authenticated content; show non-blocking offline state and retain the Home queue-status/retry control.

5. **Route all active writes through local transaction plus outbox before returning to the UI.**
   - Replace direct `useMutation(api.*)` calls in onboarding/profile/defaults, `app/mobile/app/transaction/new.tsx`, account create/rename/archive, category create/rename/icon/limit/archive/default, budget create/archive, group create, and group expense creation with typed local repository commands. Persist the optimistic entity and outbox envelope atomically, notify relevant repository queries, and only then show success/navigate; cloud delivery continues in the coordinator.
   - Include any currently server-backed settings/profile mutation in this pathway. Per-device sync-window preference remains local-only. Keep existing UI/backend input validation and show local validation errors before insert; server rejections remain visible in sync status without discarding the pending edit.
   - Keep local IDs usable by routes and relations until cloud mapping resolves; translate every Convex ID argument/payload through the mapping layer. Add `clientMutationId` to group expense and every other queued multi-row write so retries cannot duplicate groups, invites, payers, participants, or child records.

6. **Add the day-window setting and Home sync status/retry UI.**
   - Add `app/mobile/app/settings/sync.tsx` with a selectable `7`, `30`, `90`, `180`, `365` days and `All history` choice using the existing settings-screen and selected-button conventions. Explain that changing the window backfills cloud data and never removes older data already downloaded. Add a `Local sync` SettingsRow with current value in the `Data` section of `app/mobile/app/settings/index.tsx`.
   - Add a header row before `BalanceHero` in `app/mobile/app/(tabs)/index.tsx` with a top-right accessible sync icon. Reuse `IconButton`, `Sheet`, theme tokens, and centralized icon wrappers in `app/mobile/lib/icons.tsx`; do not add a tab. The icon derives from persisted queue/connection state, never placeholder React state.
   - The status Sheet reports synced/offline, pending count, active sync, failed count, and conflicts; include last successful cloud sync time. `Retry now` invokes the coordinator's manual flush and disables during an active attempt. Provide navigation to `/settings/sync`. Replace or remove the unused `app/mobile/hooks/useSyncStatus.ts` placeholder rather than keeping a second status authority.

7. **Prove local latency, history retention, and reliable cloud delivery.**
   - Use a database/repository test adapter consistent with `tests/mobile/offline.test.ts` and keep tests runnable under `app/mobile/vitest.config.ts` Node environment. Cover actual repository/outbox observable behavior, not only serializer helpers.
   - Add tests for atomic local row+queue creation and immediate subscribed read while cloud send is unresolved/offline; persisted pending status after reopen; successful retry updates cloud mapping and status exactly once; duplicate server delivery does not duplicate a transaction/group expense; dependency queue waits for local parent mapping; failed/conflict statuses and manual retry; timestamp newer-wins with older copy retained; 30-day bootstrap coverage; range cache miss invokes cloud then persists old rows; subsequent offline request for that old range uses local data; changing retention days never evicts previously fetched history; local aggregate projections match existing ledger/budget/category rules.
   - Verify in the actual Expo mobile runtime with Convex local deployment: sign in online, set 30 days, bootstrap, create a category and transaction and confirm both appear instantly before cloud acknowledgement, observe automatic cloud sync and synced icon state, disconnect cloud, create another transaction and confirm it remains visible/pending, reconnect and observe exactly one cloud record, request an older date range, then disconnect and reopen that range to confirm it is still local. Verify Home status Sheet manual retry on a forced failed entry and settings value persistence across app restart.
   - Run `bun run typecheck`, `bunx vitest run tests/mobile/offline.test.ts tests/convex tests/integration`, and the Expo runtime scenario above.

## Critical files & anchors
- `app/mobile/local/sqlite/database.ts` — current WAL database creates only outbox/drafts/localMetadata; migration and replica foundation.
- `app/mobile/local/sync/engine.ts` and `app/mobile/local/outbox/storage.ts` — disconnected queue skeleton; dispatch, durability, observable status, retry.
- `app/mobile/app/_layout.tsx` — Convex/Auth provider, offline auth gate, connection signal, coordinator lifecycle.
- `convex/schema.ts` and `convex/transactions/mutations.ts` — cloud model/cursors and only existing `clientMutationId` write contract.
- `app/mobile/app/(tabs)/index.tsx` — Home currently begins at `BalanceHero`; local query consumers and requested sync affordance.

## Assumptions & contingencies
- Initial window is 30 days; UI choices are 7/30/90/180/365 days or all history. All fetched history persists indefinitely; changing the window only adds coverage.
- The cache is hybrid: complete locally cached ranges are read from SQLite; a missing/partial requested range is fetched from cloud, cached, then served from SQLite. Cloud remains required for first sign-in, initial bootstrap, and uncached history; previously authenticated users can use their own cached data and queue edits offline.
- Every currently active cloud-backed write/read and its dependencies must use the local repository; server-only credentials and auth tables are never copied into SQLite. New unfinished/presentation-only screens do not gain invented backend features.
- Conflict resolution is timestamp last-write-wins with the losing version preserved and surfaced for review; equal timestamps prefer cloud. Device clock skew is a known limitation of the requested timestamp policy; retain both versions so a wrong clock does not destroy data.
- Device/OS suspension cannot promise an upload at the instant an app is not running. Persist work durably; sync immediately while foregrounded/connected and resume immediately on reconnect/foreground/relaunch.
